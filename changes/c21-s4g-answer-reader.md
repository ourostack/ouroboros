- The daemon can now record a person's answer to a letter from their own iMessage. Given only a message's GUID, it reads that message from the agent's BlueBubbles server and records the answer only when every check holds on the server's own fields:
  - The text is exactly the letter's code and an option number, such as `L7 2`, with an optional note after a dash. The note loses format characters and is capped at 200 characters.
  - It comes from the letter's answering handle, in that handle's one-to-one iMessage chat. It is not sent by SMS, not by the agent (a message whose direction the server doesn't state counts as the agent's), and not as a threaded reply, an edit or a retraction.
  - It was sent after the letter, timed by the server's own clock for the letter's sent message when the server has it, otherwise by the daemon's delivery time less five minutes, and before the letter's expiry.
  - Its GUID hasn't answered before. A ledger in `state/letters/answered-guids.jsonl` keeps replays and recovery passes from answering twice.

  Anything else records nothing. The daemon asks only a server on the same Mac, behind TLS, or at a tailnet address, because the fetch carries the server password. It checks the agent's bundle before reading anything for it. Each answer records whether a shell running beside the daemon could send as the person: `separate` only when the daemon runs under a macOS account other than the person's, otherwise `shared-apple-id`. The chat ingress that sends these GUIDs comes in the next change.
